# PDS requirement audit

Date: 2026-08-15

This audit separates implementation completeness from public-release evidence.
The repository contains a complete executable vertical product: mobile reader,
deterministic engine, durable local store, content compiler, signed package
installer, API, Content Studio, assets, tests, runbooks, and release gates. The
PDS defines GA more broadly than software delivery, so criteria depending on
human content, research, physical devices, legal approval, production traffic,
or accountable operations remain red until their owners attach signed evidence.

Status meanings:

- **GREEN** — implemented and exercised by reproducible repository automation.
- **AMBER** — implementation exists, but exact release-candidate, native-device,
  production-observation, or owner evidence is still required.
- **RED** — the criterion itself is not yet satisfied; code deliberately blocks
  release rather than substituting fixture or synthetic evidence.
- **N/A v1** — excluded by an accepted v1 decision and not silently promised.

## Implementation capability contract

**Capability.** A guest reader can install or open an authored Russian story,
make exactly one of four meaningful choices, recover a coherent durable run,
finish or branch it offline, and inspect what the story remembered. Editors can
author, validate, simulate, sign, and publish the same deterministic package
contract consumed by mobile and API surfaces.

**Fixed constraints and invariants.** Runtime prose is never generated: the
complete default catalog is a checked-in static artifact produced by
`npm run generate:bundled-content`; a
reachable decision has exactly four enabled authored replies; exact build IDs,
selected wording, frozen effects, state hashes, and transcript entries are
durable; content activates only after schema, checksum, signature, engine, and
storage checks; failed database migration is atomic; safety bypass never adds a
relationship penalty; private text is excluded from telemetry; release gates
cannot count fixtures or unapproved text as production inventory.

**Actors, surfaces, and lifecycle.** Guest readers use onboarding, catalog,
story disclosure, download, run, recap, branch/archive, settings, and report
surfaces. Editorial operators use Content Studio; publishers use authenticated
API routes and exact-build confirmation; operators use readiness, diagnostics,
rollback, and incident runbooks. The critical lifecycle is
`discovered → verified → installed → active → rollback`, while a reader turn is
`restored → waiting → provisional → committed → reaction/checkpoint/ending`.
Every persisted transition has an explicit failure path that retains the
previous coherent state.

The PDS route contract is also covered by stable deep-link aliases: the
story-scoped run, recap, and branches URLs resolve to the guarded canonical
surfaces, `/support/report` resolves to the consented report form, and
`/account` resolves to the explicitly local-only profile surface. Browser E2E
checks these links on both mobile viewport profiles; no account or cloud-sync
promise is introduced by the alias.

**Non-goals for v1.** Accounts, cloud merge, payments, notifications, runtime
generation, and adult-only content are excluded by accepted decisions and are
not implied by dormant compatibility fields.

**Open release evidence.** Human launch content, Russian editorial/research
results, signed native assistive-technology and minimum-device matrices,
territory legal/store approval, production signing custody/infrastructure,
penetration testing, operational ownership, and observed SLOs remain owned by
named human functions. Those are release blockers, not missing code that may be
replaced by synthetic evidence.

## Current release conclusion

The software implementation is **engineering-complete for an internal release
candidate** and its automated gates are green. The public PDS release definition
is **not yet satisfied** because AC-C01/C02, human Russian-quality/product
research, native accessibility/performance, legal/store, production key, and
live-operations evidence are external deliverables. The compiler, Studio, API,
and documentation keep those gates visibly red; no fixture, generated asset,
browser emulation, or synthetic benchmark is counted as substitute evidence.

The editorial review lane now has versioned working artifacts:
[`RUSSIAN_HOUSE_STYLE.md`](../content-style/RUSSIAN_HOUSE_STYLE.md) and
[`CHARACTER_VOICE_BIBLE_TEMPLATE.md`](../content-style/CHARACTER_VOICE_BIBLE_TEMPLATE.md).
They improve review readiness but do not satisfy native-editor approval,
blind-reader naturalness, or production content gates by themselves.
